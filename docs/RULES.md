# Detection rules

Generated by `txray rules --markdown`; do not edit by hand.
Severities are defaults: some rules raise or lower them with context
(known spender, account without code, native value attached).

## Address intelligence

| ID | Default | Title | Rationale |
|---|---|---|---|
| INT001 | critical | Interaction with a denylisted address | The address is present in the configured denylist (known drainer, scam or sanctioned address). |
| INT002 | critical | Address resembles a trusted address (address poisoning) | The address shares its leading and trailing characters with an address from the user's address book but is a different account. Attackers generate vanity addresses and seed them into the victim's history so they get copy-pasted. |

## Transactions

| ID | Default | Title | Rationale |
|---|---|---|---|
| TX001 | medium | Unlimited token allowance | The approval amount is effectively infinite; a compromised or malicious spender can move the whole balance now and in the future. |
| TX002 | high | Allowance granted to an account without code | Legitimate protocols receive approvals with contracts. Approving an EOA lets whoever holds its key pull the tokens directly. |
| TX003 | high | Operator approval for an entire NFT collection | setApprovalForAll(operator, true) gives the operator control over every token of the collection held by the signer, including tokens received later. |
| TX004 | medium | Long-lived or unlimited Permit2 allowance | Permit2 allowances with a far expiration or the maximum uint160 amount stay usable long after the interaction. |
| TX005 | medium | Selector not implemented by the target contract | The called function does not appear in the target's dispatcher; the call will reach the fallback function, which is what disguised drainer calls rely on. |
| TX006 | high | Native value sent to a function named like a drainer lure | Function names such as Claim(), SecurityUpdate() or Connect() are deployed by drainer kits to receive ETH from victims of fake airdrop pages. |
| TX007 | high | Tokens sent to the token contract itself | Most token contracts cannot send back tokens transferred to their own address; the funds are usually lost. |
| TX008 | low | Calldata sent to an account without code | The destination has no code, so the calldata is not executed. Used to carry messages, but also by phishing pages that misrepresent what is being signed. |
| TX009 | high | Called function can reach SELFDESTRUCT or DELEGATECALL | The control-flow graph of the called function reaches an instruction that can sweep the contract balance or execute arbitrary code. |
| TX010 | info | Contract deployment | The transaction creates a contract. |
| TX011 | info | Batched calls | The call wraps several inner calls; each one is analysed separately. |
| TX012 | medium | Known selector with non-canonical arguments | The selector matches a known function but the arguments are not a valid ABI encoding. Wallet UIs may display something different from what executes. |

## EIP-712 typed data

| ID | Default | Title | Rationale |
|---|---|---|---|
| SIG001 | high | Signature domain targets another chain | The domain chainId differs from the chain the wallet is connected to. |
| SIG002 | high | verifyingContract has no code | The domain names a verifying contract that does not exist on this chain. |
| SIG003 | critical | Domain impersonates a well-known protocol | The domain name is one of a known protocol (Permit2, Seaport) but the verifyingContract is not that protocol's canonical deployment. |
| SIG010 | medium | Off-chain token approval (permit) | Signing this message grants an allowance without any on-chain transaction; it does not appear in the wallet's transaction history. |
| SIG011 | high | Unlimited allowance in permit signature | The permit authorizes the maximum amount. |
| SIG012 | critical | Permit spender is an account without code | A signed permit for an EOA is the usual shape of a drainer request. |
| SIG013 | medium | Long-lived permit | The permit deadline or allowance expiration is far in the future. |
| SIG020 | medium | Permit2 allowance signature | Grants an allowance through Permit2 for one or more tokens. |
| SIG021 | critical | Permit2 batch approval to an unknown spender | A batch permit covering several tokens for a spender that is not a known router is the signature format used by most Permit2 drainers. |
| SIG022 | high | Permit2 signature transfer | PermitTransferFrom lets the spender move the tokens immediately; nothing else has to be signed. |
| SIG030 | critical | Marketplace order gives assets away | The Seaport order offers assets while the offerer receives nothing (or only zero amounts) in return. |
| SIG031 | high | Seaport bulk order signature | One signature authorizes a whole tree of orders; wallets typically display only the root. |
| SIG040 | medium | Typed data grants permissions | Unrecognized typed data containing spender/operator/delegate style fields. |

## personal_sign / eth_sign

| ID | Default | Title | Rationale |
|---|---|---|---|
| MSG001 | critical | Blind signature of a raw hash (eth_sign) | eth_sign signs an arbitrary 32-byte hash, which can be the hash of a transaction transferring the signer's assets. |
| MSG002 | high | personal_sign of a 32-byte binary value | The message is not text but a 32-byte value, typically a hash the user cannot verify. |
| MSG003 | medium | personal_sign of non-text data | The message is not valid UTF-8 text. |
| MSG010 | high | Sign-In with Ethereum domain mismatch | The SIWE message is for a different domain than the requesting site: the page may be relaying a login challenge from another service. |
| MSG011 | medium | SIWE address differs from the signer | The address in the SIWE message is not the account asked to sign. |
| MSG012 | medium | SIWE chain differs from the connected chain | The Chain ID in the SIWE message is not the wallet's current chain. |
| MSG013 | low | SIWE message outside its validity window | Expired or not yet valid according to Expiration Time / Not Before. |
| MSG014 | medium | Malformed SIWE message | The message announces itself as Sign-In with Ethereum but violates EIP-4361. |

## Bytecode

| ID | Default | Title | Rationale |
|---|---|---|---|
| BC001 | medium | SELFDESTRUCT reachable | The contract can execute SELFDESTRUCT, which sends its whole ETH balance to an arbitrary address. |
| BC002 | medium | DELEGATECALL to a dynamic target | Code from another address runs with this contract's storage and balance. |
| BC003 | low | Uses tx.origin | ORIGIN-based authorization can be abused by any contract the owner interacts with. |
| BC004 | info | EIP-1167 minimal proxy | Clone forwarding to a fixed implementation. |
| BC005 | medium | Upgradeable proxy | The executed code can be replaced by whoever controls the upgrade mechanism. |
| BC006 | low | Privileged administrative functions | The contract exposes functions such as mint, pause, blacklist or fee setters. |
| BC007 | high | Metamorphic contract pattern | CREATE2 combined with SELFDESTRUCT allows redeploying different code at the same address. |
| BC008 | info | Partial control-flow analysis | Some jump targets could not be resolved; reachability results are lower bounds. |
| BC009 | info | Hard-coded addresses | PUSH20 constants embedded in the code. |
| BC010 | info | No code at address | The account is an EOA or was destroyed. |
